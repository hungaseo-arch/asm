## 3. 이관 과정에서 드러난 것

### 3-1. 섹션 번호가 템플릿마다 다릅니다 ⚠️

작업지시서 §4-2 는 `# 1. Screen Shot` ~ `# 7. Riwayat Verifikasi` 를 상정하지만,
실제 페이지는 **세 가지 템플릿**이 섞여 있었습니다.

| 템플릿 | 건수 | 검증 이력 | 현업 답변 |
|---|---|---|---|
| 한국어 우선 | 31 | `# 7. 검증 이력` | `# 6. 현업 답변` |
| **인니어 우선** | 21 | **`# 6. Riwayat Verifikasi`** | **절 없음** |
| 혼합 | 5 | `# 7. Riwayat Verifikasi` | `# 6. Tanggapan Tim Bisnis` |

**번호로 잘랐다면 21건의 검증 이력이 `business_answer_md` 로 들어갔을 것입니다.**
파서를 제목 문자열 분류로 바꿨습니다(`scripts/import_notion.js` 의 `SECTIONS`).

§7 의 중단 조건(「섹션 제목이 §4-2 패턴과 불일치하는 페이지 5건 초과」)에 형식상 해당하지만,
구조가 완전히 파싱 가능해 중단하지 않고 처리한 뒤 보고합니다.

### 3-2. `issue_no` UNIQUE 충돌 3쌍

§4-3 대로 `(삭제)` 접두를 떼면 살아 있는 건과 겹칩니다.

```
(삭제) 48 + 48    (삭제) 50 + 50    (삭제) 52 + 52
```

삭제 후 같은 번호가 재발급된 정상 이력이므로 데이터가 아니라 제약을 고쳤습니다 —
**`db/005_issue_no_unique_partial.sql` 을 INSERT 전에 적용해야 합니다.**

### 3-3. 지시서가 정의하지 않은 절 9건

`# 0. Catatan Penomoran`(4) · `# 8. 실서버 실측`(3) · `# 8. Pengukuran Aktual`(1) ·
`# 9. Versi Bahasa Indonesia`(1). 스키마에 자리가 없어 **`findings_md` 뒤에 제목째로 보존**했습니다.
버리면 판정 근거가 사라집니다.

### 3-4. 이슈번호 체계가 설명과 다릅니다

지시서는 「01~38, 업무요건 VIII-1~6」이라 했으나 실제는 **01~60 연속 + 아카이브 3건**입니다.
`VIII-x` 번호는 존재하지 않습니다. 채번 함수는 `CSR-YYYYMM-nnn` 만 다루므로 영향 없습니다.

### 3-5. 내보내기가 6건을 빠뜨렸습니다

첫 내보내기는 CSV 전용이라 본문이 없었고, 두 번째(Markdown & CSV)에도 **63건 중 57건**만
들어 있었습니다 — 04 · 05 · 26 · 36 · 37 · 38 누락(필터된 뷰에서 내보낸 것으로 보입니다).

그 6건은 **Notion API 로 직접 받아** `import/bodies/from_api.json` 에 두었고,
스크립트가 `--extra` 로 병합합니다. 결과적으로 63건 전부 본문이 채워졌습니다.

## 4. 캡쳐(§1)를 제외한 이유

원본 이미지가 **300초 만에 만료되는 S3 서명 URL** 입니다. Drive 로 옮기려면 작업지시서 §5-4 의
Apps Script 업로드 프록시가 필요한데 그것은 **Phase 3 범위**라, 지금은 옮길 곳이 없습니다.

대신 이슈별 참조 개수를 세어 두었습니다 — **38건**(내보내기 jpeg 32 + API 확보 6).
Phase 3 에서 Apps Script 배포 후 `csr_attachments` 를 채우고 이 숫자와 대조하면 됩니다.
내보내기 폴더의 jpeg 32장이 그대로 남아 있으므로 재내보내기 없이 업로드할 수 있습니다.
