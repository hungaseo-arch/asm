### ⚠️ 회원가입 비활성이 현재 불가능합니다 (작업지시서 §6 과의 차이)

Neon Auth 화면에 이렇게 떠 있습니다 —
「Anyone on the web can sign up for your app. Support for restricted signups is coming soon.」

즉 **가입 제한 기능이 아직 제공되지 않습니다.** 작업지시서 §6 의 「회원가입 비활성」은
지금 플랫폼 수준에서 지킬 수 없습니다. 대신 **이미 설계에 방어가 들어 있습니다.**

- `002_rls_policies.sql` 의 모든 SELECT 정책이 `csr_role() IS NOT NULL` 입니다.
- `csr_role()` 은 `csr_user_roles` 에 없는 사용자에게 NULL 을 돌려줍니다.
- 따라서 **아무나 가입해도 이슈를 한 건도 볼 수 없습니다.** 목록이 통째로 빈 채로 나옵니다.

남는 위험은 데이터 노출이 아니라 **계정이 무단으로 늘어나는 것**입니다. 운영 중에는
Neon Auth → Users 를 가끔 확인해 모르는 계정을 지우십시오. Neon 이 restricted signup 을
내놓으면 그때 켜면 됩니다.

> Data API 화면의 안내도 같은 맥락입니다 — 「Provides read-write access to tables
> **without** Row Level Security enabled」. RLS 를 켜지 않은 테이블은 그대로 열립니다.
> `002` 가 6종 전부에 RLS 를 켜는 이유입니다. **`002` 를 건너뛰면 안 됩니다.**

## 2. SQL 적용

**반드시 번호 순서대로**, 한 파일씩 결과를 확인하며 실행합니다.
Neon SQL Editor 에 파일 내용을 붙여넣거나, psql 로 실행합니다.

### 먼저 `000_preflight.sql` 을 실행하십시오 (읽기 전용)

Neon Auth 가 노출하는 '현재 사용자' 함수의 이름이 `auth.user_id()` 가 맞는지 확인합니다.
`002` 의 `csr_role()` 은 만들 때 본문이 파싱되므로, 이름이 다르면 **첫 줄부터 실패**합니다.

- **점검 3 이 `OK — auth.user_id() 호출 가능`** 이면 그대로 `001` 부터 진행하십시오.
- **`실패`** 가 뜨면 점검 2 의 함수 목록을 알려 주십시오. `002`·`003` 의 세 곳
  (`csr_role()` 본문 · `NEW.updated_by` · `changed_by`)만 실제 이름으로 바꿔 드리겠습니다.
- 점검 4 에 `authenticated` 가 보여야 `002` 의 GRANT 가 실행됩니다.

```bash
# psql 로 실행할 경우 (연결 문자열은 Neon 콘솔 → Connection Details)
psql "postgresql://...neon.tech/neondb?sslmode=require" -f db/000_preflight.sql
psql "postgresql://...neon.tech/neondb?sslmode=require" -v ON_ERROR_STOP=1 -f db/001_schema.sql
psql "..." -v ON_ERROR_STOP=1 -f db/002_rls_policies.sql
psql "..." -v ON_ERROR_STOP=1 -f db/003_triggers.sql
# 004 는 §3 을 먼저 끝낸 뒤에 실행합니다.
```

| 파일 | 만드는 것 | 성공 확인 |
|---|---|---|
| `000_preflight.sql` | (읽기 전용) 선행 점검 | 점검 3 이 `OK` |
| `001_schema.sql` | 테이블 6종 · 인덱스 · `csr_next_issue_no()` | 아래 §4 점검 1 |
| `002_rls_policies.sql` | `csr_role()` · RLS 활성 · 정책 16종 · GRANT | 아래 §4 점검 2 |
| `003_triggers.sql` | 컬럼 가드 · 상태 로그 트리거 | 아래 §4 점검 3 |
| `004_seed_roles.sql` | 역할 3계정 등록 | 3행 조회 결과 |

> **`003` 까지 끝내면 Data API 화면의 `Refresh schema cache` 를 누르십시오.**
> Data API(PostgREST)는 스키마를 캐시해 두기 때문에, 갱신하지 않으면 방금 만든 테이블이
> 404 로 나옵니다.

> 각 파일은 `BEGIN … COMMIT` 으로 감싸 두었습니다 — 중간에 실패하면 통째로 되돌아가므로
> 원인을 고쳐 같은 파일을 다시 실행하면 됩니다. `CREATE … IF NOT EXISTS` 와
> `DROP POLICY IF EXISTS` 를 써서 **여러 번 실행해도 안전합니다**.

## 3. 계정 3종 생성 (나중에 — C-6 보류)

계정 생성은 뒤로 미뤘습니다(2026-09-10). **§1·§2 는 계정 없이도 끝까지 진행됩니다** —
`001`~`003` 은 이미 적용·검증을 마쳤고, 계정이 준비되면 `004` 만 이어서 돌리면 됩니다.

1. Neon 콘솔 → Auth → Users → **Create user** 로 3개 계정을 만듭니다.

   | 역할 | 용도 | 이메일 |
   |---|---|---|
   | `admin` | 역할 관리 · 상태 로그 조회 · 전 컬럼 편집 | (C-6) |
   | `it_dept` | IT부서 회신 · 상태/담당자/목표일만 편집 | (C-6) |
   | `business` | 이슈 등록 · 현업 답변 · 검증 · 첨부 | (C-6) |

   > `admin` 과 `it_dept` 는 **서로 다른 계정이어야 합니다.** 작업지시서 §9 의 완료 조건이
   > 「it_dept 계정으로 `verification_result` 변경 시도 → 실패」 확인이라, 한 계정이 겸하면
   > 컬럼 가드가 실제로 막는지 검증할 수 없습니다.

2. `db/004_seed_roles.sql` 상단의 **이메일 3줄만** 실제 값으로 바꿉니다.
   User ID 는 적을 필요가 없습니다 — `neon_auth."user"` 에서 이메일로 자동 조회합니다.

3. `004` 를 실행합니다. 마지막 조회가 **3행**이면 완료입니다.

## 4. 적용 후 점검 (작업지시서 §9)

> **`db/verify.sql` 하나만 실행하면 아래 점검 1~3 이 한 번에 돕니다** (읽기 전용).
> 결과 표를 그대로 알려 주시면 판정해 드리겠습니다. 아래는 개별 점검 원문입니다.


**점검 1 — 테이블 6종**

```sql
SELECT table_name FROM information_schema.tables
 WHERE table_schema = 'public' AND table_name LIKE 'csr!_%' ESCAPE '!'
 ORDER BY 1;
-- 기대: csr_attachments, csr_issues, csr_it_replies,
--       csr_status_log, csr_user_roles, csr_verifications  (6행)
```

**점검 2 — RLS 가 6종 전부에 켜져 있는지**

```sql
SELECT relname, relrowsecurity FROM pg_class
 WHERE relnamespace = 'public'::regnamespace AND relname LIKE 'csr!_%' ESCAPE '!'
 ORDER BY 1;
-- 기대: 6행 모두 relrowsecurity = true
```

**점검 3 — 트리거 2종**

```sql
SELECT tgname FROM pg_trigger
 WHERE tgrelid = 'public.csr_issues'::regclass AND NOT tgisinternal
 ORDER BY 1;
-- 기대: csr_issues_column_guard, csr_issues_status_log
```

**점검 4 — 권한 차단이 실제로 되는지 (작업지시서 §9 필수 항목)**

`it_dept` 계정으로 로그인한 상태에서 Data API 로 아래를 시도하면 **실패해야 합니다.**

```sql
-- it_dept 세션에서: 현업 전용 컬럼을 건드림 → 42501 로 거부되어야 정상
UPDATE public.csr_issues SET verification_result = '조치확인 / Terkonfirmasi' WHERE id = 1;
-- 기대 오류: CSR: column verification_result not editable by role it_dept
```

```sql
-- business 세션에서: Open 을 바로 Verified 로 → 거부되어야 정상
UPDATE public.csr_issues SET it_status = 'Verified' WHERE it_status = 'Open';
-- 기대 오류: CSR: it_status Open -> Verified not allowed for role business
```

> 성공해 버리면 003 이 적용되지 않았거나 해당 계정이 `admin` 으로 등록된 것입니다.
